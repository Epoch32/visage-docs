> **Roadmap Disclaimer:** This roadmap describes a tentative architectural direction, not a fixed release commitment. Features, implementation details, priorities, and release targets are subject to change as Visage evolves and technical feasibility is evaluated.

Visage was created with an uncompromising philosophy: **zero virtual DOM overhead, zero runtime dependencies, and browser-native primitives**. As Visage evolves through the 2.x series and toward a potential **Visage 3.0**, our focus is on expanding standards support, eliminating unnecessary tooling, and exploring new approaches to resumability and native application development.

Our goal is to make standards-compliant behavior a first-class part of the toolkit, allowing developers to build efficient, secure, and interoperable applications without reinventing established protocols or relying on unnecessary abstractions.

## Core Architectural Commitments

## Current Phase: Visage 2.x Series

The 2.x series focuses on **standards support, full-stack ergonomics, security, and a lean compilation pipeline**. The objective is to make standards-based functionality easier to use through Visage while keeping the framework itself small and dependency-light.

### 1. HTTP and API Standards

Implement and integrate relevant IETF standards across Visage's request handling, data-fetching, routing, and server-side infrastructure.

- **HTTP Semantics and Caching, RFC 9110 and RFC 9111:** Support correct conditional requests, entity-tag validation, cache directives, and resource revalidation. Integrate with native browser caching rather than duplicating functionality unnecessarily.
- **Problem Details, RFC 9457:** Provide consistent handling of structured HTTP API errors across client requests, server actions, route loaders, and development tooling.
- **Digest Fields, RFC 9530:** Explore standards-compliant content integrity verification for HTTP requests and responses, with explicit trust and verification policies.
- **Web Linking, RFC 8288:** Support parsing and consuming HTTP link relations for pagination, resource discovery, and navigation between related API resources.
- **Structured Field Values, RFC 9651:** Provide reusable TypeScript utilities for parsing and serializing standardized HTTP header fields.
- **Early Hints, RFC 8297:** Explore server-generated `103 Early Hints` responses and compiler-assisted preload discovery for SSR performance, subject to deployment platform support.
- **Deprecation and Sunset, RFC 9745 and RFC 8594:** Surface API lifecycle metadata through optional development diagnostics and application-level tooling.

These are candidate integration targets, not a claim that every RFC is already implemented. Support may consist of native platform integration, server-side functionality, or a first-party TypeScript implementation, depending on the standard.

### 2. Standards-Based Web Platform Integration

Prefer established browser APIs over framework-specific replacements wherever practical.

- **View Transitions API:** Integrate browser-native transitions into navigation and supported UI updates.
- **Speculation Rules API:** Explore declarative prerendering and prefetching for eligible navigations.
- **Popover API and CSS Anchor Positioning:** Support native popovers, anchored overlays, and lightweight positioning patterns.
- **WHATWG Streams:** Use native streams for streaming responses, SSR output, and efficient processing of request and response bodies.
- **Content Security Policy:** Generate and validate production CSP configurations, including script hashes where appropriate, while accounting for deployment-specific policies and runtime requirements.

### 3. Compiler and Tooling Simplification

Reduce unnecessary build complexity without compromising standards compliance or developer experience.

- **Lean Vite + Babel Pipeline:** Consolidate the JSX compiler around Babel and Vite's plugin interface, minimizing auxiliary tooling and AST dependencies where feasible.
- **In-House Markdown and Frontmatter:** Explore a lightweight Markdown compiler and frontmatter parser to reduce the dependency footprint of documentation tooling.
- **Build-Time Syntax Highlighting:** Prefer compact, build-time semantic tokenization over heavyweight client-side syntax-highlighting engines where it meets feature requirements.
- **Semantic Compiler Diagnostics:** Use compiler analysis to identify opportunities for standards-compliant resource loading, cache handling, and security configuration.

### 4. Security and Production Hardening

- **Automated CSP Assistance:** Analyze generated assets and help synthesize restrictive Content Security Policy directives and hashes, with explicit handling of dynamic scripts, external resources, and deployment constraints.
- **Zero-FOUC Storage Preboot:** Provide an early theme initialization strategy that minimizes visual flicker while respecting CSP and storage availability.
- **Protocol-Aware Diagnostics:** Surface useful development warnings for malformed headers, deprecated resources, invalid cache policies, and other detectable standards integration issues.

## Future Milestone: Visage 3.0.0

**Visage 3.0 is a tentative long-term vision, not a committed feature set.** It explores architectural changes that may extend Visage beyond conventional JavaScript-centric full-stack frameworks.

<FeatureGrid>
  <FeatureCard icon="layers" title="Fine-Grained Resumability">
    Investigate serializing sufficient reactive and execution metadata during SSR to resume application behavior without unnecessarily re-executing component initialization. The long-term goal is to minimize client JavaScript and defer code loading until it is needed.
  </FeatureCard>

  <FeatureCard icon="activity" title="Efficient Native IPC">
    Explore lower-overhead communication between a Zig host and embedded WebViews, potentially using shared memory where platform security rules and runtime constraints permit.
  </FeatureCard>

  <FeatureCard icon="database" title="Local-First Reactive Stores">
    Investigate CRDT-backed synchronization and embedded SQLite-compatible storage for offline-first applications, with consistent state integration across supported hosts.
  </FeatureCard>

  <FeatureCard icon="smartphone" title="Cross-Platform Native Hosts">
    Explore Android WebView and iOS WKWebView integrations alongside desktop targets, aiming to reuse application code while respecting each platform's native constraints.
  </FeatureCard>
</FeatureGrid>

These initiatives depend on technical validation, platform compatibility, security review, and community feedback. In particular, zero-JavaScript resumability, zero-copy native IPC, and sub-10MB native executables are research goals rather than guaranteed outcomes.

## Standards Support Policy

Visage intends to prioritize standards according to practical utility, interoperability, security, implementation complexity, and compatibility with its supported environments.

- **Native integration first:** Prefer browser, runtime, and server implementations where they already provide the required behavior.
- **First-party implementations where useful:** Implement missing application-level functionality in TypeScript when doing so adds meaningful value without unnecessary dependencies.
- **Graceful degradation:** Account for differences between browsers, server runtimes, CDNs, and native hosts. Features requiring platform support should not be assumed universally available.
- **No blanket compliance claims:** Support for an RFC may be partial, optional, or environment-specific. Each implementation should document its supported requirements and limitations.
- **Incremental adoption:** RFCs and APIs may be added, deferred, or removed from the roadmap as standards evolve and implementation experience improves.
