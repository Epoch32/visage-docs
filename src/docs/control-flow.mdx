Because Visage components execute **exactly once** at mount time, traditional JavaScript expressions like ternary operators `condition ? <A /> : <B />` and `items.map()` do not automatically re-evaluate when signals change. Instead, Visage provides reactive control flow primitives: `<Show>`, `<For>`, and `<Index>`.

<FeatureGrid>
  <FeatureCard icon="split" title="Fine-Grained DOM Splicing">
    <code>&lt;Show&gt;</code> and <code>&lt;For&gt;</code> insert DOM comment markers to splice nodes in place, cleanly disposing internal reactive scopes when branches hide or items are removed.
  </FeatureCard>

  <FeatureCard icon="list-ordered" title="Keyed Item Reuse">
    <code>&lt;For&gt;</code> reuses existing DOM elements across array reorders and mutations. When an item moves or the array is sorted, existing DOM nodes simply reposition rather than re-creating.
  </FeatureCard>
</FeatureGrid>

## Conditional Rendering (&lt;Show&gt;)

The `<Show>` component conditionally renders its children based on the truthiness of the `when` prop. It supports an optional `fallback` prop for falsey states:

<CodeBlock
  filename="ShowExample.tsx"
  lang="tsx"
  code={`import { Show, createSignal } from "@epoch32/visage";

function Profile() {
  const [user, setUser] = createSignal<{ name: string } | null>(null);

  return (
    <Show
      when={user}
      fallback={<button onClick={() => setUser({ name: "Alice" })}>Log In</button>}
    >
      {(item) => <div>Welcome back, {item().name}!</div>}
    </Show>
  );
}`}
/>

## Keyed List Reconciliation (&lt;For&gt;)

The `<For>` component renders a list of items with fine-grained referential stability. The children render callback receives the raw item along with a reactive `index` accessor function:

<CodeBlock
  filename="ForExample.tsx"
  lang="tsx"
  code={`import { For, createSignal } from "@epoch32/visage";

function FruitList() {
  const [fruits, setFruits] = createSignal(["Apple", "Banana", "Cherry"]);

  return (
    <ul>
      <For each={fruits} fallback={<li>No fruits available</li>}>
        {(fruit, index) => (
          <li>
            #{() => index() + 1}: {fruit}
          </li>
        )}
      </For>
    </ul>
  );
}`}
/>

## Custom Keying with the by Prop

By default, `<For>` tracks items by object reference. When working with server APIs that return fresh object references on every refetch, use the `by` prop to track items by unique ID:

<CodeBlock
  filename="ForByKeyExample.tsx"
  lang="tsx"
  code={`import { For } from "@epoch32/visage";

interface User {
  id: string;
  name: string;
}

function UserDirectory(props: { users: () => User[] }) {
  return (
    <ul>
      <For each={props.users} by={(user) => user.id}>
        {(user, index) => (
          <li key={user.id}>
            Row #{() => index() + 1}: {user.name}
          </li>
        )}
      </For>
    </ul>
  );
}`}
/>

## Position-Indexed Lists (&lt;Index&gt;)

While `<For>` binds DOM nodes to item references, `<Index>` binds DOM nodes to **array positions**.

In `<Index>`, the index passed to children is a fixed `number`, while the item is a reactive signal `() => T`. When an item's value at a given position changes, only the signal for that slot fires, without moving or re-creating DOM elements:

<CodeBlock
  filename="IndexExample.tsx"
  lang="tsx"
  code={`import { Index, signal } from "@epoch32/visage";

function TagEditor() {
  const tags = signal(["typescript", "visage", "reactive"]);

  return (
    <div class="tags-container">
      <Index each={tags} fallback={<span>No tags added</span>}>
        {(tag, index) => (
          <div class="tag-slot">
            <span>Slot #{index}:</span>
            {/* tag is a reactive signal () => string */}
            <span>{tag}</span>
          </div>
        )}
      </Index>
    </div>
  );
}`}
/>

## Type Narrowing with Accessor Children

In TypeScript, if your `when` condition evaluates a nullable object (such as `User | null`), you can pass a callback as the child. Visage supplies a narrowed accessor `() => User` where `null` and `undefined` are guaranteed to be filtered out:

<CodeBlock
  filename="type-narrowing.tsx"
  lang="tsx"
  code={`interface User {
  id: string;
  name: string;
  email: string;
}

const [currentUser, setCurrentUser] = createSignal<User | null>(null);

<Show when={currentUser} fallback={<div>Guest User</div>}>
  {/* 'user' is guaranteed to be an Accessor<User> (non-null!) */}
  {(user) => (
    <div>
      <h3>{user().name}</h3>
      <p>{user().email}</p>
    </div>
  )}
</Show>`}
/>

## Why Not Ternaries or .map()?

Developers coming from React often wonder why standard JavaScript loops and conditionals are discouraged in Visage JSX:

  <table className="doc-table">

        <th>React (Virtual DOM)</th>
        <th>Visage (Fine-Grained DOM)</th>

    </thead>
    <tbody>
      <tr>
        <td><code>items.map()</code></td>
        <td>Re-runs on every render; diffs entire array</td>
        <td>Only runs once on mount; does not track changes</td>
      </tr>
      <tr>
        <td><code>&lt;For each=&#123;items&#125;&gt;</code></td>
        <td>Not standard</td>
        <td>Reuses existing DOM nodes; updates indices surgically</td>
      </tr>
      <tr>
        <td><code>&lt;Index each=&#123;items&#125;&gt;</code></td>
        <td>Not standard</td>
        <td>Pins DOM to slot index; updates item signals without moving nodes</td>
      </tr>
      <tr>
        <td><code>condition ? &lt;A /&gt; : &lt;B /&gt;</code></td>
        <td>Re-evaluated on every component re-render</td>
        <td>Runs once; static unless wrapped in a function</td>
      </tr>
      <tr>
        <td><code>&lt;Show when=&#123;c&#125;&gt;</code></td>
        <td>Not standard</td>
        <td>Creates comment markers; disposes inactive scopes</td>
      </tr>
    </tbody>
  </table>
</div>

<Callout type="tip" title="The Scope Disposal Guarantee">
  When a <code>&lt;Show&gt;</code> flips to false or an item is removed from <code>&lt;For&gt;</code>, Visage automatically disposes all effects and signal subscriptions created inside that subtree. You never have to worry about detached DOM nodes listening to global signals in the background.
</Callout>
